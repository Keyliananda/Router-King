## Scope

Dieses Dokument beschreibt einen konkreten MVP fuer die Steuerung von FreeCAD durch einen externen AI-Assistenten wie Claude oder Codex.
Der Fokus liegt nicht auf einem allgemeinen "Python in FreeCAD ausfuehren", sondern auf einer belastbaren Tool-Schnittstelle, die auch RouterKing-spezifische Funktionen und spaeter weitere Custom Workbenches ansprechbar macht.

## Zielbild

Ziel des MVP ist eine lokale Architektur, in der:

- FreeCAD weiterhin das ausfuehrende System bleibt.
- RouterKing als FreeCAD-Addon unveraendert im FreeCAD-Kontext lebt.
- Ein MCP-Server aussen eine stabile, deklarative Tool-Oberflaeche anbietet.
- Der Assistent keine FreeCAD-Interna erraten muss.
- Riskante Aktionen wie Maschinensteuerung oder freier Code klar getrennt und abgesichert werden.

Der MVP soll folgende Kernfaehigkeit liefern:

1. Ein Assistent kann den aktuellen FreeCAD-Kontext lesen.
2. Ein Assistent kann RouterKing-Aktionen gezielt ausloesen.
3. Ein Assistent erhaelt visuelles Feedback per Screenshot.
4. Maschinennahe Aktionen bleiben bestaetigungspflichtig.

## Empfehlung

### Basis-Repository

Empfohlene Basis fuer einen Fork:

- `neka-nat/freecad-mcp`

Gruende:

- Reifer als ein reines `run_script`-Bridge-Modell.
- Bereits produktnahe MCP-Tools statt nur freier Codeausfuehrung.
- Screenshot-Unterstuetzung ist vorhanden und fuer Agent-Steuerung wichtig.
- Trennung zwischen FreeCAD-Addon und MCP-Server ist bereits angelegt.
- Aktiver und groesserer Upstream als die kleineren Alternativen.

### Nicht als Primaerschnittstelle verwenden

- `bonninr/freecad_mcp` ist als Referenz nuetzlich, aber als Ausgangsbasis fuer RouterKing zu roh.
- Freies `run_script` oder `execute_code` soll nur ein Dev-/Recovery-Fallback sein, nicht der Normalweg.
- GUI-Klick-Automation ist fuer RouterKing nur Notfallwerkzeug, nicht Architektur.

## Warum dieser Schnitt zu RouterKing passt

RouterKing hat bereits die richtige Kernabstraktion:

- ein Addon ausserhalb von FreeCAD-Core
- ein lokales Action-System fuer AI-gesteuerte Aenderungen
- Trennung zwischen AI-, CAM- und Maschinenlogik

Bestehende Anknuepfungspunkte:

- `RouterKing/ai/actions.py` enthaelt bereits deklarative Aktionen fuer Geometrie, CAM und Maschine.
- `README.md` beschreibt `routerking_actions` schon als JSON-basiertes Protokoll.
- `docs/ARCHITECTURE.md` definiert RouterKing bereits sauber als Workbench/Add-on ausserhalb von FreeCAD-Core.

Der MVP soll diese vorhandene Struktur nach aussen oeffnen, statt eine zweite, konkurrierende Automationsebene zu bauen.

## MVP-Architektur

```text
Claude / Codex / anderer MCP-Client
              |
              v
     RouterKing MCP Server
     - deklarative Tools
     - Session / Validation
     - Confirm / Preview / Undo
              |
              v
      FreeCAD RPC Bridge
      - lokaler Host
      - verbindet sich mit laufendem FreeCAD
      - kein offener Remote-Exec per Default
              |
              v
      FreeCAD + RouterKing Addon
      - bestehende Workbench
      - RouterKing actions
      - CAM / G-Code / GRBL
```

## Grundprinzipien

### 1. Declarative First

Der Assistent arbeitet primaer mit fachlichen Tools wie:

- `routerking_apply_actions`
- `routerking_generate_gcode`
- `routerking_cam_generate_job`
- `routerking_machine_jog`

Nicht primaer mit:

- `run_script`
- `execute_code`
- "sende diesen Python-String nach FreeCAD"

### 2. Visual Feedback Required

Nach aendernden Aktionen soll der MCP-Server nach Moeglichkeit einen Screenshot oder mindestens einen aktualisierten Szene-Report zurueckgeben.

### 3. Risk Segmentation

Es gibt drei Risikoklassen:

- `read`: nur lesen
- `modify`: Modell oder CAM veraendern
- `machine`: reale Maschinenaktion

`machine`-Tools muessen im MVP immer explizit bestaetigt werden.

### 4. RouterKing vor Generic FreeCAD

Fuer RouterKing-Funktionen soll der Assistent nicht direkt FreeCAD-Basisobjekte zusammenstueckeln muessen, wenn es bereits eine RouterKing-Domaenenaktion gibt.

## MVP-Scope

### Im Scope

- Lokaler MCP-Server fuer FreeCAD + RouterKing
- Verbindung zu laufendem FreeCAD
- Kontext lesen
- RouterKing-Aktionen ausloesen
- Screenshot-Funktion
- bestaetigungspflichtige Maschinen-Tools
- einfacher Undo-/Transaction-Rahmen fuer Modell-Aenderungen
- klare Tool-Schemas fuer den Assistenten

### Ausserhalb des MVP

- Vollstaendige allgemeine Automatisierung aller beliebigen Workbenches
- Multi-User-Remote-Zugriff
- Rechteverwaltung ueber mehrere Benutzer
- frei programmierbare Makro-Generierung als Standardpfad
- Cloud-Ausfuehrung
- semantische Suche ueber komplette FreeCAD-Doku
- autonome Langzeit-Agenten mit Job-Queue

## Konkrete MVP-Tools

### A. Core Context Tools

Diese Tools muessen zuerst stehen, damit der Assistent ueberhaupt weiss, woran er arbeitet.

1. `list_documents`
2. `get_active_document`
3. `get_scene_info`
4. `get_selection_context`
5. `capture_view`

Erwarteter Nutzen:

- Dokumentname, Objekte, Typen, aktive Auswahl, Labels
- falls vorhanden: Skizzenstatus, Constraints, sichtbare Fehler
- visuelle Kontrolle nach Aktionen

### B. RouterKing Domain Tools

Diese Tools bilden den eigentlichen Mehrwert des MVP.

1. `routerking_list_actions`
2. `routerking_apply_actions`
3. `routerking_analyze_selection`
4. `routerking_optimize_splines_preview`
5. `routerking_generate_gcode`
6. `routerking_cam_generate_job`

Regel:

- `routerking_apply_actions` ist der generische Domain-Einstieg.
- Die spezialisierten Tools bleiben zusaetzlich sichtbar, damit das Modell stabile, gut benannte Werkzeuge bekommt.

### C. Machine Tools

Diese Tools nur mit Confirm und klarer Statusrueckgabe.

1. `routerking_machine_connect`
2. `routerking_machine_disconnect`
3. `routerking_machine_request_status`
4. `routerking_machine_jog`
5. `routerking_machine_stream_gcode`
6. `routerking_machine_stop`

Pflichtfelder:

- `confirm`
- bei Bewegungen oder Streaming zusaetzlich `reason`

### D. Dev Fallback

Nur fuer Entwicklung und nur explizit aktivierbar:

1. `routerking_run_script`

Restriktionen:

- standardmaessig deaktiviert
- nur lokal
- deutlich als unsicher markiert
- spaeter optional mit Allowlist / Sandboxing / Audit Log

## Tool-Schemas fuer den MVP

### `routerking_list_actions`

Zweck:

- Gibt die offiziell unterstuetzten RouterKing-Aktionen und Parameter zurueck.

Rueckgabe:

- Action-Name
- Kurzbeschreibung
- erforderliche Parameter
- optionale Parameter
- Risikoklasse

### `routerking_apply_actions`

Zweck:

- Fuehrt einen oder mehrere RouterKing-Action-Eintraege aus.

Input:

```json
{
  "actions": [
    {
      "type": "create_part_box",
      "length": 20,
      "width": 30,
      "height": 5,
      "name": "TestBox"
    }
  ],
  "preview": false,
  "capture_view": true
}
```

Rueckgabe:

- Erfolg / Fehler je Action
- erzeugte oder veraenderte Objekte
- Screenshot wenn verfuegbar
- aktualisierter Selection-/Scene-Context

### `routerking_machine_jog`

Input:

```json
{
  "dx": 0,
  "dy": 0,
  "dz": 5,
  "feed": 300,
  "confirm": true,
  "reason": "Z-Achse fuer Sichtpruefung anheben"
}
```

Rueckgabe:

- Kommando gesendet / verweigert
- aktueller Maschinenstatus
- letzte bekannte Position falls verfuegbar

## Sicherheitsmodell fuer den MVP

### Standard

- nur lokale Verbindung
- kein Remote-Zugriff per Default
- kein freies Python als Standard-Tool
- Maschinenbefehle nur mit `confirm=true`
- Logging aller `modify`- und `machine`-Aktionen

### Optional spaeter

- Allowlist fuer Remote-IPs
- gesonderter "dangerous tools" Modus
- API-Key oder Session-Token zwischen MCP-Server und FreeCAD-Bridge
- Audit-Trail pro Session

## Visuelles Feedback

Screenshots sind fuer den MVP kein Luxus, sondern Bestandteil der Rueckgabe.

Mindestens in diesen Faellen:

- nach `routerking_apply_actions`
- nach `routerking_cam_generate_job`
- nach groesseren Geometrie-Aenderungen

Fallback:

- wenn Screenshot im aktuellen View nicht moeglich ist, Text-Hinweis plus aktualisierter Szene-Status

## Umgang mit Custom Workbenches

Der MVP soll RouterKing direkt abdecken und gleichzeitig spaeter auf weitere Workbenches erweiterbar bleiben.

Dafuer gilt:

- Workbench-Features werden nicht automatisch aus Python-Imports "magisch" entdeckbar.
- Fuer stabile Assistenten-Nutzung braucht jede Workbench eine explizite Tool-Flaeche oder ein dokumentiertes API-Schema.
- Das Discovery-Feature fuer spaetere Workbenches sollte eher "welche registrierten Tools/Capabilities gibt es?" liefern als "welche Python-Module sind importierbar?".

Vorschlag fuer spaeteres Discovery-Tool:

- `list_workbench_capabilities`

Rueckgabe:

- Workbench-Name
- registrierte Actions oder Tools
- benoetigte Parameter
- GUI-Abhaengigkeit ja/nein
- Risikoklasse

## Akzeptanzkriterien

Der MVP ist erfolgreich, wenn alle folgenden Punkte erfuellt sind:

1. Claude oder Codex kann sich per MCP mit lokalem FreeCAD verbinden.
2. Der Assistent kann den aktuellen Dokument- und Auswahlkontext lesen.
3. Der Assistent kann mindestens drei RouterKing-Aktionen erfolgreich ausfuehren.
4. Nach aendernden Aktionen wird visuelles oder textuelles Feedback geliefert.
5. G-Code kann ueber RouterKing generiert werden.
6. Maschinen-Tools verweigern Ausfuehrung ohne explizites `confirm=true`.
7. Freier Python-Exec ist nicht der Standardpfad.

## Bewusste Nicht-Ziele im MVP

- kein vollautonomer Agent ohne Bestaetigung
- kein universeller Support fuer jede externe FreeCAD-Workbench
- keine offene TCP-Schnittstelle ins LAN ohne Schutzmechanismen
- keine API, die Assistenten zum Schreiben beliebiger Makros ermutigt

## Offene technische Entscheidungen

Diese Punkte muessen frueh geklaert werden:

1. Soll der Fork zunaechst ausserhalb von RouterKing leben oder direkt ins Repo?
2. Soll die Verbindung weiter auf XML-RPC basieren oder spaeter vereinheitlicht werden?
3. Wo wird Screenshot-Logik am saubersten verankert: im Fork oder im RouterKing-Bridge-Modul?
4. Wie viel Undo/Transaction wird im MVP garantiert?
5. Ob `routerking_run_script` ueberhaupt im ersten Release sichtbar sein soll.

## Empfohlene naechste Umsetzungsschritte

1. Fork von `neka-nat/freecad-mcp` anlegen.
2. Minimale RouterKing-Bridge definieren.
3. Read-only-Tools zuerst implementieren.
4. Danach `routerking_apply_actions` auf vorhandene Action-Handler mappen.
5. Erst danach CAM- und Machine-Tools freischalten.

## Fazit

Der richtige MVP ist kein "Claude darf Python nach FreeCAD senden", sondern:

- ein lokaler MCP-Server
- mit klaren, deklarativen Tools
- auf Basis eines vorhandenen FreeCAD-MCP-Forks
- gekoppelt an die bestehende RouterKing-Action-Schicht
- mit visuellem Feedback und Sicherheitsregeln

Das liefert schnell echten Nutzen, bleibt aber technisch kontrollierbar und ist die beste Grundlage, um spaeter weitere Custom Workbenches strukturiert anzubinden.
